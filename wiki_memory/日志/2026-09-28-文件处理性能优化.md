# 文件处理性能优化

## 目标与依据

用户要求改善副开发机上的扫描、同步、压缩耗时，但不得降低主机效率或文件处理质量。当前机器只读查询为 i7-11800H、约 16 GiB 内存；使用隔离临时数据采样，没有访问真实仓库。剖析及三轮对照定位到归档重复祖先查询、同卷小文件线程调度、反向等价记录重复提交和部署 JSON 缩进编码。

## 实现

- 版本 2.5.2。归档只读阶段使用既有最多 16 项/250 ms 的 `ReadScope`，每个叶子保留实时状态，目录结束复核与所有内容/清单屏障不变；写入 ZIP 时仍逐文件完整检查来源路径链。
- 同卷 ≤64 KiB 文件直接在原任务线程暂存，大文件及异卷保留有界 worker；暂存所有权、关闭后完整 SHA-256、原子提交、异常清理、停止删除和 SQLite 完成记录不变。
- 反向扫描使用已经持久保存的精确等价记录，不再逐文件重复写入；完整校验仍先退役两方向旧记录，profile 隔离保持不变。
- 事务日志紧凑编码一次写入，保留认证值、修订、`fsync` 和原子替换；旧缩进格式经新实例认证及恢复测试。
- 扩展合成基准覆盖 ZIP 预览与完整执行、不同压缩级别、32 MiB 混合数据和独立反向扫描；完整结果与边界见[性能验证](../../docs/性能验证.md)。

## 验证与交付

- 最终业务源码全量测试：528 passed、11 skipped，91.11 秒；跳过项均为当前 Windows 无符号链接创建权限。
- 三轮中位数：900 个小文件 ZIP 预览 1.3006 → 0.3092 秒，执行 2.0799 → 1.0726 秒；同卷小文件镜像 −8.5%、无视频备份 −12.7%；32 MiB 同步约持平。2,000 文件第一次反向基线扫描 0.2976 → 0.1601 秒。
- 新增覆盖小/大文件调度分界、两个 profile 的反向免重复写入、归档阶段之间来源变化、哈希期间新增文件、共享祖先期间叶子替换，以及紧凑/缩进认证日志互读。
- 对整体基准中增量扫描 +8.6% 的波动补做同文件、交替旧/新只读检查实现的受控对照，各三轮中位数 0.6065 / 0.6074 秒（+0.15%）；首次旧实现 1.4477 秒明显高于后两次。保留完整原始对照数字，不声称首次增量扫描提速。
- 全量覆盖继续验证两方向来源只读、长路径、取消、复制/校验失败停止删除、异卷流水线汇合、部署恢复与 HMAC 篡改拒绝，以及七页三尺寸布局。
- `memory_lint.py index` / `check` 通过，55 篇 Markdown 页面。
- 基于最终源码运行 `tools/build.py` 成功；重建前核对本工作区精确 EXE 路径，保留干净子进程 PATH。`dist/ObManage.zip` 为 49,777,337 字节；全包 CRC 通过，EXE、`_internal`、使用说明和许可证直接位于根层，随包指南与源码字节一致。
- 冻结 EXE 在隔离状态启动 `.Archive` 页面并生成原生截图，退出码 0；另执行 40 文件完整内容 CLI 预览，数据库产生 40 条等价记录、两个测试端全部文件不变，日志无错误。首轮验证脚本自身未关闭 SQLite 连接导致临时目录清理失败，显式关闭后重跑通过，不属于应用失败。
