# ObManage 记忆维护协议

本文件适用于 `wiki_memory/`，与仓库根目录的协作约定共同使用。源码、测试、用户明确要求和已验证的运行结果是事实来源；记忆保存结论及其来源。

## 开始任务

1. 读取本文件及 `当前状态/` 的项目概览、系统架构、当前约束、当前待办。
2. 按任务阅读相关 `active` 决策、知识页和已知问题。
3. 需要追溯时才查 `日志/MOC_工作日志.md` 和相关历史，不默认加载全部日志。
4. 修改前核对实际代码和 Git 状态；记忆与实现不一致时先查明原因，不能用旧日志覆盖当前事实。

启动记忆包尽量保持在约 6,000 tokens 内。当前状态只放未来协作必需的简短结论。

## 写入和授权

- `当前状态/`、`决策/`、`知识/` 保存长期有效内容；`日志/` 保存单次任务的审计摘要。
- 用户已明确要求建立本工程记忆，并要求每次完整对话产生的修改都提交并推送。已有代码证据的事实、用户本轮及此前明确授权的约束，可直接写入 `active`；不得为重复确认这些事实停工。
- 尚未验证的推测或未被任务授权的新架构方案使用 `proposed`，说明依据与待验证条件；需要新增授权时集中提出，不能冒充现行决策。
- 每个长期页面填写 `source_logs`，正文链接相关源码、测试或决策。记录可核对的行为，不把“测试计划”写成“测试通过”。
- 每个主题保留一个有效版本。结论变化时更新当前状态；决策被替代则保留旧页并标为 `superseded` 或 `deprecated`，新页填写 `supersedes`。
- 不批量删历史，不记录完整聊天、隐藏推理、凭据、个人仓库文件名、机器用户名或私有绝对路径。代码来源用仓库相对 Markdown 链接，环境位置用 `%LOCALAPPDATA%` 等通用表示。

## 任务结束

1. 为实质任务创建 `日志/YYYY-MM-DD-任务标题.md`，只写本轮目标、决策、改动、实际验证、结果和后续事项。混合任务按主要交付物选择一个 `kind`。
2. 工作中日志为 `draft`，补齐实际证据后才封存为 `archived`。封存后更正用新日志链接旧记录；不能提前写“打包成功”或“推送完成”。
3. 更新受影响的当前状态、决策、知识，清理已完成待办。未完成项明确保留，不用绿色检查代替完成审计。
4. 运行 `python wiki_memory/工具/memory_lint.py index` 和 `check`。修改工具时另运行其标准库测试。
5. 检查 diff，按用户约束提交本轮相关修改并推送当前分支，再核对远端提交。命令失败要明确报告，不得虚报已推送。不要夹带与本轮无关的用户修改、运行数据库、真实数据预览或构建产物。

提交先于推送，日志不预言尚未发生的推送。可以把待推送日志随实现提交，完成后在最终答复提供已核对的提交与远端状态；如需把远端验证补入日志，用随后一次文档提交并再次推送。

## 页面格式

长期页面和日志都包含 YAML frontmatter：`type`、`status`、`kind`、`importance`、`updated`（真实日期）、`topic`、`source_logs`（列表）、`supersedes`（无替代时为 `null`）。模板页自身不参加事实检查。

- `type`：`state`、`decision`、`knowledge`、`log`、`moc`。
- `status`：`active`、`proposed`、`deprecated`、`superseded`、`archived`；`draft` 用于未封存日志。
- 日志 `kind`：`feature`、`ui`、`bug`、`discussion`、`test`、`maintenance`；长期页另可用 `architecture`、`process`、`module`、`operations`。
- `importance`：`high`、`medium`、`low`。`topic` 使用稳定标识，不按日期改名。

页面正文优先标准 Markdown 相对链接以便 GitHub 阅读；`source_logs` 可用根相对 wiki 链接。路径使用 `/`。不维护分类子日志索引。

## 固定操作

- 记忆同步：更新本轮日志及已授权的长期结论，刷新索引。
- 记忆检索：先读当前状态，再按主题查知识和日志。
- 记忆体检：运行 lint，修复本轮造成的缺字段、断链或重复主题。
- 记忆压缩：归纳重复历史到长期页，保留原日志和来源关系。
