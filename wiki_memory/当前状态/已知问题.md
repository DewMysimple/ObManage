# 已知问题与验证边界

| 已知边界 | 实际影响 / 应对 | 依据 |
| --- | --- | --- |
| 日常快速扫描使用元数据快照 | 内容发生变化而受检查元数据仍完全相同，可能继续跳过；用“完整内容校验”先退役旧记录并重新读取两端 | [engine.py](../../obmanage/engine.py)、[深度校验测试](../../tests/test_engine.py) |
| Windows 内核磁盘读取可能长时间阻塞 | 取消会在读取调用返回后生效；异卷并行任务会安全等待两个 worker 退出，不能从 Python 强杀一个永久不返回的设备 I/O | [并行哈希实现](../../obmanage/engine.py)、[优化日志](../日志/2026-09-11-完整内容校验并行优化.md) |
| exFAT 在提交改名后可能重发文件 ID | 1.2.1 在目标大小有效但身份或时间变化时重新校验最终路径内容；摘要不符仍失败并停止删除 | [engine.py](../../obmanage/engine.py)、[回归测试](../../tests/test_engine.py)、[修复日志](../日志/2026-09-11-exFAT提交校验修复.md) |
| Windows 只读目标文件会拒绝删除或覆盖 | 1.2.2 只对仍匹配预览且仅有一个硬链接的目标普通文件解除 `ReadOnly` 后重试；非只读权限错误、对象替换、状态变化和多硬链接均失败，来源及目录属性不修改 | [engine.py](../../obmanage/engine.py)、[回归测试](../../tests/test_engine.py)、[修复日志](../日志/2026-09-11-Windows只读目标处理修复.md) |
| 无跨全仓库事务或文件系统快照 | 取消、失败保留已完成部分；重新分析后继续。路径复核与最终文件系统变更之间仍有极窄并发窗口，使用者持续修改仓库时可能要求重试，不能承诺任何并发下整体瞬时一致 | [执行与复核](../../obmanage/engine.py) |
| 故障自动测试使用注入 | 断盘、卷身份变化、空间不足及占用错误已有模拟；模拟通过不能声称覆盖所有真实 USB 设备和文件系统故障 | [test_engine.py](../../tests/test_engine.py)、[test_roundtrip.py](../../tests/test_roundtrip.py) |
| 大文件按整个文件复制 | 改变的视频会整文件复制，未改变的视频可跳过；没有块级增量 | [复制模块](../../obmanage/engine.py) |
| 只镜像普通文件内容和目录结构 | 不保留 ACL、备用数据流、历史版本，不跟随符号链接或重解析点 | [paths.py](../../obmanage/paths.py)、[复制实现](../../obmanage/engine.py) |
| 空间检查按本轮待复制总大小 | 预检可能比逐文件释放旧版本后的实际峰值需求更保守；当前优先在执行前报明确空间错误 | [execute 的 disk_usage 检查](../../obmanage/engine.py) |
| 普通路径 API 存在极窄并发竞态 | 引擎在扫描、打开、提交和删除前后反复检查物理身份与重解析点，但无法仅靠 Python 路径 API 绝对阻止同账户恶意进程恰在检查与操作之间替换 junction；正常使用应关闭其他写入者，失败后重新分析 | [路径保护](../../obmanage/paths.py)、[部署引擎](../../obmanage/management/deployment.py) |
| 回收站直接清理不可撤销 | 用户确认后不创建隔离副本；权限错误、取消、执行期变化或断电可能留下部分清理结果。程序报告已删除数量和逻辑内容大小，但无法恢复已删除项；重新扫描后再处理剩余内容 | [直接清理](../../obmanage/management/trash.py)、[页面结果](../../obmanage/pages/trash_cleanup.py) |
| 本机 HMAC 不等于权限隔离 | 部署与升级前遗留隔离记录能拒绝单文件损坏、孤立路径替换和未授权字段变化；已经能任意读写状态目录和仓库的同账户程序也能直接破坏密钥与数据，超出该完整性机制的威胁边界 | [部署记录](../../obmanage/management/journal.py)、[遗留隔离兼容](../../obmanage/management/trash.py) |
| 遗留隔离认证密钥丢失时恢复会 fail closed | 升级前已有回收站 journal 或备份但密钥缺失/残缺时，兼容恢复和新的直接清理都会拒绝；需要保留状态目录和日志人工排查，不应删除旧记录后强行继续 | [遗留密钥处理](../../obmanage/management/trash.py) |
| 任一持久记录损坏会整体 fail closed | 一个损坏的部署 journal/grant、遗留隔离 journal、未知临时记录或缺少 journal 的孤立备份，可能连带阻止其他合法批次恢复及所有新写入；这是避免“跳过坏状态继续写”的安全取舍。保留应用状态目录、目标卷事务目录和日志，确认依据后人工修复，不要重建密钥绕过 | [部署记录](../../obmanage/management/journal.py)、[遗留状态审计](../../obmanage/management/trash.py)、[恢复门禁](../../obmanage/ui.py) |
| 突然断电或强拔盘的卷级落盘顺序未证明 | 部署记录和关键文件会 flush/fsync，重命名前也持久标记恢复阶段；但目录项、跨文件顺序和移动盘缓存没有卷级 flush 保证。回收站直删不承诺事务一致性，断电后必须重新扫描 | [部署事务](../../obmanage/management/deployment.py)、[回收站直接清理](../../obmanage/management/trash.py) |
| 崩溃窗口可能留下未登记的自有临时项 | 尚未来得及写入授权记录的 key 临时文件、stage 或新建父目录不会被程序猜测删除；已知父目录残留会显示为 `rolled_back_with_residuals`，其他 `.obmanage-deploy-*` 保留项需结合日志人工判断 | [部署记录](../../obmanage/management/journal.py)、[部署事务](../../obmanage/management/deployment.py) |
| Obsidian 打开仓库读取是本机配置快照 | 明确识别为打开的目标会阻止部署；配置不可读或含异常时无法证明目标空闲，页面要求用户额外确认，仍不能替代关闭 Obsidian 和其他写入工具 | [分发页面](../../obmanage/pages/distribution.py)、[仓库目录](../../obmanage/management/catalog.py) |
| 持久恢复副本占用空间 | 部署 backup 和升级前遗留回收站隔离内容会一直保留到用户撤销、恢复或单独确认永久清理；左侧恢复门禁会暂停新写入。新回收站直接清理不再增加隔离占用 | [ADR-006](../决策/ADR-006-多页面管理与回收站直接清理.md) |

顶部拥挤、重复相对路径列和右侧宽度问题已在 1.2.0 修复，不再列为未解决缺陷。四列表格、列分隔线及长路径访问由[布局测试](../../tests/test_ui_layout.py)覆盖，并完成原生 Windows 普通窗口、较小窗口和真实最大化验证；具体证据见[本轮日志](../日志/2026-09-10-工程记忆与界面整理.md)。
