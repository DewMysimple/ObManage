## 2.8.1｜异常场景与最终复核精修

本轮先从不可变提交 `2bb5c3e0f42e6b9583f171cf79777783df6a799b` 加载 2.8.0，对未改扫描源码的工作区做自对照。24 个独立仓库加一个嵌套仓库的权限异常中位耗时为 1.935 / 1.942 秒，首次为 3.905 / 3.939 秒。原始记录位于本机 `artifacts/scan-281-before.json`。后续每阶段都用同一固定基线和相同输入交替测量。常规场景的本地 Git 快照为 `f1f2a715e2188829c4efa3e0c7e3e85bd22a0d96`。合并重复故障提示并更新版本标识后，另以最终扫描源码快照 `26082cff04748479afaa85ae2da526924b8ef7e3` 复测两组权限异常。

B 阶段 92 项专项通过。诊断 A/B 中，正常复扫的末次枚举保持 510 次，元数据请求保持 13,592 次，清单物化 100 → 0 次，完整清单比较 100 → 50 次。末次墙钟中位数 1.0938 → 1.0853 秒，线程 CPU 中位数 1.0781 → 1.0625 秒。首次、复扫、单文件变动的末次墙钟下降约 6–9 毫秒，任务总耗时在测量波动范围内。记录为 `artifacts/scan-281-stage-b.json`。

C 阶段 108 项专项通过。最终计数 A/B 中，首次增量的路径 `lstat` 为 38,057 → 37,133 次，`DirEntry.stat` 为 5,116 → 5,116 次。每轮少 924 次实际查询，其中末次少 462 次。元数据统计少 563 次。新增分类诊断默认关闭，开启后仅记录聚合调用、失败和耗时，不输出路径或正文。`metadata_queries` 只合计诊断覆盖的底层 `lstat`、`stat` 和 `DirEntry.stat`，`snapshot`、祖先链及标记是归因层，不能再次相加。目录枚举和 Win32 内部调用也不能换算为物理磁盘 I/O 次数。

正常增量两版均只开一个 SQLite 连接。故障场景均为确定性注入。两端目录故障复现了 2.8.0 曾出现的第二轮扫描开销，2.8.1 的两种权限异常均零数据库连接、零内容比较、零末次枚举。历史记录的 +80.1% 来自另一组 2.7.1 对照和数据集，本表比较本轮同一夹具的 2.8.0。发现阶段从请求取消到返回的中位延迟约 0.200 → 0.043 毫秒，实际设备的阻塞读取延迟未测。

末次清单比较与物化的累计耗时约 4.01 → 0.85 毫秒。完整末次复核的诊断墙钟没有稳定提速证据，已确认的收益是减少 462 次查询并保留原有 510 次真实枚举。诊断模式本身增加计数和计时开销。24 仓库的首次增量在诊断 A/B 为 3.753 → 3.813 秒，关闭诊断为 3.624 → 3.627 秒，归档预览的计数也保持相同。12 仓库关闭诊断的首次、无变化复扫和同大小修改分别为 1.940 → 1.913、1.240 → 1.213 和 1.291 → 1.227 秒。两组结果支持正常任务基本持平或小幅缩短，不能外推到移动硬盘。

原始逐轮记录位于本机忽略目录 `artifacts/`。24 仓库用 `scan-281-24-counted.json`、`scan-281-24-timing.json`，12 仓库用 `scan-281-12-counted.json`、`scan-281-12-timing.json`。最终权限故障复测为 `scan-281-final-fault-counted.json` 和 `scan-281-final-fault-timing.json`。复测本机时运行下节命令并省去 `--test-parent`，对关闭诊断的耗时另加 `--timing-only`，将 `--vaults` 改为 12 可测较小集合。

首次、无变化复扫、同大小修改和深度扫描用每版本各自的 SQLite 库。相同输入下核对双向清单、操作项和授权状态，统计核对严格 UTF-8 字符数与类型汇总。故障专项覆盖两端目录和 marker 失败、迭代与元数据异常、真实 junction、目录及设备身份变化、末次新增仓库和文件变化。另验证两端仓库零写、无已授权计划、扫描句柄和 SQLite 连接释放，以及下一次扫描能正常开始。执行前的整批预检、逐仓库复核和删除屏障沿用原实现。

### 在专用设备上复现

本轮仅在本机 NVMe SSD 的 NTFS 临时目录验证，未实测物理 USB 或 exFAT。可在已有且明确授权的专用测试目录运行以下命令。先核对目录和卷，替换示例盘符及路径，确认该目录位于预期设备且不在任何真实仓库内。

```powershell
Get-Item -LiteralPath 'X:\ObManageBenchmark'
Get-Volume -DriveLetter X
.\.venv\Scripts\python.exe tools\benchmark_scanning.py --vaults 24 --files 40 --repeats 3 --test-parent 'X:\ObManageBenchmark' --output artifacts\scan-281-device.json
```

`--test-parent` 只在该目录内创建并清理由脚本生成的新临时子目录，移动端合成仓库写在那里，本机端合成仓库和 SQLite 留在本机临时目录。工具只分析合成仓库，从 Git 只读加载基线。想比较关闭诊断的墙钟耗时，可另用 `--timing-only` 和不同的输出文件。记录文件系统、SSD 或 HDD、连接方式和缓存状态，默认缓存未控制。设备身份变化可用 `tests/test_scanning_incremental.py` 的 `volume_replaced` 故障注入验证，测试只使用临时目录。

未加入跨页历史缓存。现有结果已由各自页面管理，新增缓存需要额外的路径、设备及任务失效规则，本轮证据集中在扫描本身。归档、部署及回收站仍使用各自的执行器。

## 阶段 0–1：初始测量

Windows / Python 3.14，本机临时目录，12 个独立仓库加一个嵌套仓库，每仓库 30 个小型 UTF-8 笔记、配置文件、256 KiB 附件、视频及空目录。两个版本交替执行三轮；操作系统缓存未受控制，没有模拟或声称 USB 实测。

原实现首次分析中位数 1.6761 秒，无变化复扫 1.1547 秒；每轮均为 588 次目录枚举、3,214 条枚举记录。复扫有 13,585 次 Python 元数据查询，首次有 18,917 次；首次完整哈希 924 次，读取 8,261,176 字节（嵌套父子范围有重叠读取）。元数据统计 0.3430 秒、精确字符统计 0.4134 秒，均有 268 次枚举。该组是优化前证据，不是最终收益表。

同组首轮中，初始与末次镜像清单合计约 0.49 秒；SQLite 打开约 0.020 秒、写入约 0.039 秒；完整哈希流约 0.023 秒。计时可能嵌套，不能相加当成互斥耗时。此小文件数据上，遍历及元数据相关固定成本比哈希流明显；大附件、冷磁盘和 USB 的组成仍需另测。

`ScanMetrics` 默认关闭，仅显式激活或开启 `obmanage.scan` DEBUG 日志时收集任务级聚合。日志不含仓库路径、文件名或正文。基准同时从真实 `os.scandir`、`os.lstat`、`os.stat`、`DirEntry.stat` 和实际内容读取计数，确保旧版与新版使用相同口径；这些是 Python API 请求数，不宣称是磁盘硬件 I/O 次数。

```powershell
.\.venv\Scripts\python.exe tools/benchmark_scanning.py --vaults 12 --files 30 --repeats 3 --output artifacts/sharedscan.json
```

基准通过 Git 只读导出固定提交，在临时目录用独立包名加载；不会切换工作区或维护第二套生产扫描器。测试也使用该独立引用比较仓库集合、完整文件/目录快照、排除项、问题代码及统计结果。

## 扫描会话的可信度

`ScanSession` 属于一个任务 epoch，有明确关闭动作，关闭时释放全部目录观察；不保留 `DirEntry`，不建立跨任务持久清单。发现阶段可用枚举元数据，进入内容清单前升级为现有 `snapshot()` 的完整字段。

Windows 实测 `DirEntry.stat()` 的 inode/device 为零，因此绝不把这些值送入镜像计划。清单使用独立路径快照；目录观察有枚举前后状态，任何异常形成不完整结果。只读统计可以报告部分结果，写操作消费清单前必须 `require_complete()`。

相邻调用可以传入刚完成的祖先链检查及目录状态，避免立即重复同一检查；这不扩展到写入阶段。末次复核必须重新枚举实时文件系统，不能将旧会话自身当成复核结果。

- 阶段 3：发现/统计接入任务会话，新旧独立对照及相关专项共 60 项通过。首次方案减少枚举但重复祖先检查导致耗时退化，已修正；最终收益仍以验收数据为准。
- 阶段 4：`SyncEngine` 抽取比较器，增量页接入双端集合初次采集、单一 SQLite 连接及真实集合末次复核。双方向不再重复比较；执行前整批预检及串行写入保留。

| [store.py](../obmanage/store.py) | 一次增量任务共用连接；逐文件提交、双方向/模式隔离、旧数据库格式、外部修改检测和异常回滚不变。打开共享连接前重新核验状态位置与双端分离，初始化或关闭失败仍释放连接/任务锁。 |
| [tasking.py](../obmanage/tasking.py)、[reading.py](../obmanage/reading.py) | 沿用 `FeatureWorker(QThread)`，只增加可选聚合与有界 worker 的诊断上下文传递；SHA-256 仍读到 EOF。 |

仓库选择器及其他扫描页面通过原 `discover_vaults()` 自动使用共同底座；其工作线程、导航、按钮、确认次数和后续授权流程均未重写。没有跨任务哈希缓存、持久仓库索引或新的后台监听器。

首次两版均完整哈希 **2,236 份文件版本、15,841,384 字节**；父/子仓库的内容比较仍按业务分别进行，没有以复用目录观察代替内容读取。无变化复扫均无需重新哈希；少量修改均只读取两份文件版本、1,920 字节。精确统计均读取 960,000 字节，关闭字符统计均为零。数据库连接从每轮 25 次减为 1 次，逐文件持久提交保持。

目录枚举不是唯一收益指标：增量清单枚举减少约 26%，路径元数据请求仅小幅减少。更多收益来自共享首次目录观察及初始化；没有将查询数下降幅度当成总耗时下降幅度。正常增量场景约缩短 9%–11%，统计约缩短 6%–8%。

异常场景故意在每个笔记分组制造权限失败，两版均显式报告不完整并阻止写入。新版还进行集合结束复核，因此该场景耗时上升；不能将此结果当作全面提速。取消场景均在第三次发现进度发出取消，约 14 ms 返回，实际设备阻塞 IO 的取消延迟未验证。归档最终仍为原遍历，耗时基本持平。
